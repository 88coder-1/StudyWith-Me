▶ intro2se-w4-model.fig · What is UML?
ONE SHARED VOCABULARY OF PICTURES

UML: a standard set of diagrams, not one diagram

What it is

Unified Modeling Language — a standard notation (OMG/ISO) so any two engineers draw the same shape for the same idea, instead of inventing their own boxes and arrows.

Two families

Structural — the shape of the data/parts (class, component, deployment). Behavioral — the flow of actions and interactions (use case, activity, sequence, state machine).

Year-1 scope

We use 3 of the ~14 UML diagram types. That's enough to go from a requirement to something buildable.

DiagramFamilyAnswersWhen
Use caseBehavioralWhat can actors do?Today
Class / entityStructuralWhat data shape do we need?Today
ActivityBehavioralIn what order, with what branching?Today
SequenceBehavioralWhich object sends which message, in order?Week 5–6
Component / deploymentStructuralHow do the running pieces fit together?Week 5

Same rule as everywhere else this term: pick the smallest notation that answers the question you actually have.

▶ intro2se-w4-model.fig · Use-case notation
FOUR PIECES · YEAR-1 SCOPE

Use-case diagram: the pieces and the rule

Actor

Who or what external thing interacts with the system — a role, not always a person.

Use case

One thing the system does for an actor. Name it verb + object.

The rule that trips everyone up

Association (solid line) connects actor ↔ use case only. «include» connects use case ↔ use case only — never touches an actor.

Next few slides: actor types, naming, and «include» vs «extend» — each with its own worked example.

Solid = association (actor↔use case). Dashed = «include» (use case↔use case only).

▶ intro2se-w4-model.fig · Actors: two kinds
NOT EVERY ACTOR IS A PERSON

Primary actor vs system (secondary) actor

Primary actor

Starts the use case to get a goal accomplished. Usually a human role — but always ask "who wants this to happen?"

System / secondary actor

An external system the use case depends on, but which never starts it on its own. Mark it «system» so it isn't mistaken for a person.

Same test either way

If it is outside the box you are building and it exchanges information with your system, it is an actor — human or not.

DomainPrimary actorSystem / secondary actor
StudyMate (reminders)Student«system» AI Service (parses natural language)
Food deliveryCustomer«system» Payment Gateway
Library loansMember«system» Library Catalog System

Both kinds use the same solid association line to a use case — the stereotype label is just a note for the reader, not a different notation.

Same discipline as FR-writing in Week 3: a bare noun hides what actually happens. If you can't put a verb in front of it, it probably isn't one use case yet.

▶ intro2se-w4-model.fig · «include»
A STEP THAT ALWAYS HAPPENS

«include»: mandatory, shared behaviour

Meaning

The base use case always performs the included one — every single time, no exception. Arrow points from base → included.

Why pull it out

Either the step is reused by more than one use case, or splitting it keeps each box focused on one job.

Another example

Checkout «include» Validate Cart — you cannot check out without the cart being validated first, ever.

Base (Checkout) points to included (Validate Cart) — always executed.

▶ intro2se-w4-model.fig · «extend»
A STEP THAT ONLY SOMETIMES HAPPENS

«extend»: optional, conditional behaviour

Meaning

The base use case is already complete without it. The extension only runs when its condition is met. Arrow points from extension → base.

Why it's different from «include»

«include» = always happens. «extend» = happens sometimes, at a named extension point, under a stated condition.

Another example

Apply Discount Code «extend» Place Order — condition: "customer entered a promo code before confirming."

Extension (Apply Discount Code) points back to base (Place Order) — runs only if the condition holds.

Same two use cases, one wrong connection

✓ Right

▶ intro2se-w4-model.fig · Why classes
NOUNS BECOME BOXES

Class / entity diagram: what data does this need?

The trick

Underline the nouns in your FR/AC sentences. A noun that must be remembered between sessions is a candidate entity.

Year-1 scope

Boxes hold attributes only — no methods yet. Behaviour is Week 6 (construction).

Every line needs a number

Multiplicity (1, *) says how many of one side relate to one of the other.

From FR-3

"a reminder 1 day before a deadline"

Nouns: student, task, due date, reminder → candidate classes: Student, Task, Reminder.

▶ intro2se-w4-model.fig · StudyMate class diagram
STUDENT 1──* TASK *──1 COURSE · TASK 1──* REMINDER

StudyMate: the class / entity diagram

Read each line as "one X has how many Y": one Student has many Tasks · many Tasks sit in one Course · one Task has many Reminders.

▶ intro2se-w4-model.fig · Traps
SAY IT OUT LOUD BEFORE YOU DRAW

Three class-diagram traps

No methods in the box yet — attributes only. Behaviour is Week 6.
Multiplicity on the wrong side flips the meaning — read "one X has how many Y", every line, every time.
A calculated value ("days until due") is not a field — it is computed when needed, not stored.

Same discipline as FR-writing: say the rule out loud before you commit it to the diagram.

▶ intro2se-w4-model.fig · Activity diagrams
THE THIRD GAP: NEITHER USE CASE NOR CLASS ANSWERS THIS

Use case = what · class = what data · activity = in what order

What you have so far

A use case and some data

Get Reminder exists (use case). A Task has a status (class). Neither says what happens first, second, or when the answer branches.

What an activity diagram adds

Steps, decisions, and endings

A picture of the control flow inside one use case — including the branching your FR's acceptance criteria already imply.

Not the same as a sequence diagram (which object sends which message, in order) — that needs an architecture to point at, so it waits for Week 5–6. Activity diagrams need only the FR you already have, so we cover them fully today.

▶ intro2se-w4-model.fig · Key points
TAKEAWAYS · THEN STUDIO

What to remember

A model is a map of the requirement — check it against the FR, not against your imagination.
Association = actor↔use case. «include»/«extend» = use case↔use case. Never mix them.
Class diagrams: nouns → boxes, attributes only, multiplicity read as "one X has how many Y".
Activity diagrams answer "in what order, with what branching" — sequence diagrams (which object messages whom) wait for Week 5–6.
AI may draft the diagram. You verify every oval and every box traces to a real FR.
