▶ intro2se-w2-process.fig · Activity 1
SWEBOK KA · SOFTWARE REQUIREMENTS

Activity 1 — Software Specification

Definition

Understanding and defining what services are required and the constraints on the system's operation and development.

The "what" and "why"

Elicitation — talk to stakeholders (needs vs wants). Analysis — check feasibility, conflicts, consistency. Specification — document the agreement formally.

Key artifact

The Requirement

A condition or capability needed by a user to solve a problem or achieve an objective.

Understand the problem before solving it.

▶ intro2se-w2-process.fig · Activity 2
SWEBOK KAs · DESIGN & CONSTRUCTION

Activity 2 — Software Development

Converting the specification into an executable system — a two-stage process.

Stage 1 · the skeleton

Software Design

Defining the architecture, components, interfaces, and data structures. Design is a problem-solving activity.

Stage 2 · the body

Software Construction

The detailed creation of working software through coding, verification, unit testing, and debugging.

From blueprint to executable.

▶ intro2se-w2-process.fig · Activity 3
SWEBOK KAs · TESTING & QUALITY

Activity 3 — Software Validation

Verification & Validation (V&V) show that a system conforms to its specification and meets the customer's expectations.

Verification

"Building it right?"

Does the code meet the spec? Are there bugs?

Validation

"Building the right thing?"

Does the software actually solve the user's problem?

Scope: goes beyond "finding bugs" — includes performance, security, and usability testing.

▶ intro2se-w2-process.fig · Activity 4
SWEBOK KA · SOFTWARE MAINTENANCE

Activity 4 — Software Evolution

Definition

The process of changing the system after it has gone into use. Software is never "done" — as the business changes, the software must adapt.

Types of maintenance

Corrective — fixing discovered faults. Adaptive — adapting to new environments (e.g. a new OS). Perfective — improving performance or maintainability.

Key concept

Technical Debt

Compromises made during development to save time — that increase the cost of future maintenance.

v1.0 → v2.0 · adaptation to change.

▶ intro2se-w2-process.fig · Waterfall
PLAN-DRIVEN

The Waterfall model

Concept

Plan-driven — complete one phase before the next. Known as "Big Design Up Front".

Best for

Critical systems (aerospace, medical devices) where requirements are well-understood and stable.

Pros

Clear milestones · easy to manage · excellent documentation.

Cons

Change is expensive · working software appears late.

Progress flows downward; feedback to earlier phases is costly.

▶ intro2se-w2-process.fig · Incremental
ADAPTIVE

Incremental development

Specification, development, and validation are interleaved. The system grows through usable versions, with the most valuable functionality delivered first.

Each increment: plan → build → validate → collect feedback.

Every cycle delivers a working version—not just documents.

Pros

Early customer feedback · lower risk of failure.

Cons

Process can be invisible/messy · architecture can degrade.

Best for

Business software · startups · rapidly changing requirements.

▶ intro2se-w2-process.fig · Case study
APPLYING THEORY TO PRACTICE

Case study: UX Insight Auditor

The Project

Building an AI tool that scans user interfaces (UIs) and automatically flags usability errors.

The Challenge

How do we apply the "software process" concepts to build this effectively?

Context

High uncertainty — we don't know exactly how the AI will perform yet.

UX Insight Auditor

Scan · flag · report

The tool scans a UI and raises issues like a low-contrast button — ⚠ Contrast Error — for the designer to fix.

▶ intro2se-w2-process.fig · Spec & V&V
CLOSING THE LOOP

From vague idea to verified product

Applying specification · the what

Bad spec: "The AI should check the UI." (too vague)

Good spec: "The system shall identify if text contrast ratios fall below WCAG 2.1 standards." (testable)

Applying validation · the check

Unit test: does the contrast-math function return the correct ratio?

User validation: does a designer find the error report useful or annoying?
