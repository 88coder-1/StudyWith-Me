▶ intro2se-w6-construction.fig · Construction fundamentals
FIVE THINGS GOOD CODE DOES · SWEBOK

Five fundamentals of construction

These are the goals behind every "good practice" you'll hear. The first three are what we work on today; the last two you already met (reuse a library; follow a style).

The one to remember: minimize complexity — a human has to read this code later, and that human is often you.

1

Minimize complexity

Simple, readable code > clever code. This drives almost every other rule.

2

Anticipate & embrace change

Build so the next change is easy — agile, small pieces, clear seams.

3

Construct for verification

Write code so bugs are easy to find — standards, logs, testable shape.

4

Reuse assets

Use existing libraries/components instead of reinventing — but only trusted ones.

5

Apply standards

Naming, layout, error handling — a shared style so the team reads as one.

▶ intro2se-w6-construction.fig · Minimize complexity
FUNDAMENTAL #1

Simple & readable beats clever

❌ Clever — nobody can read it
def a(t,l): return [x for x in l if (x['d']-now()).days<=1 and not x['c']]

One line, cryptic names, does three things. A bug here is invisible.

✅ Readable — one job, clear names
def tasks_due_soon(tasks): # due within 1 day and not done (FR-3) soon = [] for task in tasks: days_left = (task.due_date - today()).days if days_left <= 1 and not task.done: soon.append(task) return soon

More routes through a function = more places a bug can hide, and more cases a test must cover.

Cyclomatic complexity (McCabe, 1976) is just a way to count those routes — more branches = harder to test and understand. So: fewer branches, smaller functions, clearer names. Rule of thumb: one function does one thing.

▶ intro2se-w6-construction.fig · Readable code
FUNDAMENTAL #5 · APPLYING STANDARDS (LIGHT)

Readable code & naming

DO

Name for meaning

tasks_due_soon, not a. A name should say what it is without a comment.

Small functions

If you can't see the whole function on one screen, split it.

One consistent style

Agree on naming/format across the team — let a formatter enforce it.

DON'T

Cryptic abbreviations

t, l, tmp2 — future-you won't remember what they meant.

Comment the obvious, hide the tricky

Explain why, not what. Delete dead code, don't comment it out.

Copy-paste the same block 5×

Duplication = five places to fix the same bug. Make it a function.

This is light today — the point is habits, not a style rulebook. AI writes cleaner code when your prompt asks for readable names and small functions.

Rule of thumb: if you need a comment to explain a name, the name isn't done yet. Ask your AI for clear names in the prompt — it will follow.

▶ intro2se-w6-construction.fig · Naming, properly
FUNDAMENTAL #5 · CODE COMPLETE + PYTHON

Naming, done properly

1

Just-right length (Goldilocks)

Gorla & Benander (1990): debugging was easiest when names averaged 10–16 characters. Not x / tmp; not roll_no_of_a_student.

2

Loop variables

i, j, k are fine for short loops. Used outside the loop or nested? Give it a real name — record_count.

3

Use opposites precisely

begin/end, min/max, first/last, next/previous — consistent pairs read faster.

Python naming conventions

KindStyleExample
Variable / functionsnake_casedue_date, add_task()
ClassPascalCaseTaskRepository
ConstantUPPER_SNAKEMAX_TASKS
Module / packagelowercasetasks.py

Code is read far more than it's written — favour read-time clarity. And tell your AI the convention in the prompt, so its draft matches your codebase.

▶ intro2se-w6-construction.fig · Part 2 · Version control
THE PROBLEM VERSION CONTROL SOLVES

You've already lived this pain

Naming chaos

report_final_v2_FINAL_really.docx

Which one is the real one? Version control gives you one file with a full history.

Overwrite

"You saved over my part!"

Two teammates edit the same file. Git merges both — or tells you exactly where they clash.

Mystery bug

"It worked yesterday…"

Git shows what changed, when, and by whom — and lets you go back to a working version.

Version control is not optional in a real team. It's the save button for the whole project's history.

▶ intro2se-w6-construction.fig · What Git tracks
GIT = A TIMELINE OF SNAPSHOTS

Every commit is a snapshot with a reason

$ git log --oneline a1b2c3d feat: add task with due date (FR-1) ← Priya · 2h ago 9f8e7d6 fix: reject empty task title (FR-1) ← Nan · yesterday 4c5b6a7 feat: mark task done (FR-2) ← Aran · yesterday 0011223 chore: initial project structure ← Priya · 2 days ago

Each line answers what changed, who, when, and — from the message — why. This log is your project's memory.

In plain terms · a word you'll meet

SWEBOK calls each tracked file a "configuration item" — that just means every file that makes up the product: code, tests, docs. Keeping them all versioned together is a real engineering job, not just using a tool.

THE ONE LOOP YOU'LL REPEAT ALL SEMESTER

Edit → stage → commit → repeat

In plain terms · think of a box

git add = put the changes you want into a box · git commit = seal & label the box (one snapshot + a message that says why) · git push = ship the box to the team on GitHub. Keep boxes small and pack them often.

▶ intro2se-w6-construction.fig · A good commit
THE GOLDEN THREAD, IN YOUR COMMIT LOG

A good commit is small, and says why

✅ Good
feat: add task with due date (FR-1) - validate the title is not empty - store due_date as an ISO date - return the new task id

One logical change. First line = type + what + the FR it delivers.

❌ Bad
stuff fixed it asdf update (200 files changed)

Says nothing; bundles everything. A reviewer — and future-you — is lost.

Rule for this course: reference the FR in the message — feat: … (FR-1). That's the Golden Thread reaching all the way into your history: Problem → FR → Design → commit.

▶ intro2se-w6-construction.fig · Branch & merge
WORK IN PARALLEL WITHOUT BREAKING MAIN

A branch is a safe parallel line

Branch

Split off

git branch feat/add-task — work without touching main.

Commit

Build there

Commit freely on your branch; main stays stable for everyone.

Merge

Bring it back

When it's done and reviewed, merge into main.

In plain terms

A branch is like doing "Save As" on the whole project so you can experiment freely. If it works, you merge it back into main; if it doesn't, you throw the copy away and main was never touched.

▶ intro2se-w6-construction.fig · Merge conflict
WHEN TWO PEOPLE EDIT THE SAME LINES

A merge conflict is normal — read it, don't fear it

<<<<<<< HEAD # your version max_tasks = 50 ======= max_tasks = 100 # your teammate's version >>>>>>> feat/limits # the other branch

Git is telling you: "you both changed this line — you decide which is right." Open the file, pick (or combine) the correct code, delete the <<</===/>>> markers, then commit the resolution.

In plain terms

It's like two people editing the same sentence in one shared document. Git doesn't guess — it pauses and asks you which wording to keep. Nothing is lost or broken; you just choose, then save.

⚠️ Never "fix" it with git push --force — that erases a teammate's work instead of resolving the clash. Never force-push a branch other people share.

▶ intro2se-w6-construction.fig · Pull request
THE TEAM'S QUALITY GATE

A Pull Request = "please review, then merge"

Push branch
feat/add-task
→
Open PR
propose the change
→
Teammate reviews
reads the diff, comments
→
Merge to main
after approval

The PR shows the diff — exactly what lines changed. A teammate reads it before it reaches main. This is where code review lives (we go deeper in Week 9).

In plain terms

A Pull Request is like handing your homework to a classmate to check before you turn it in to the teacher (main). They read it, suggest fixes, and only then does it become part of the shared project.

Why it matters: no single person can quietly break main, and everyone learns the codebase by reading each other's changes.

SWEBOK · SCM · WHAT TO TRACK, WHAT TO HIDE

NEVER COMMIT

Generated junk

▶ intro2se-w6-construction.fig · StudyMate · FR-1
WORKED EXAMPLE · IMPLEMENT "ADD TASK" (FR-1)

Generate → read → commit

1 · The prompt (FR + rules)

Write add_task(title, due_date) for StudyMate. FR-1: a student adds a task with a title and a due date. - title must not be empty → ValueError - due_date is ISO 'YYYY-MM-DD' - return the new task as a dict + id Keep it simple and readable.

2 · Read the draft, then commit

def add_task(title, due_date): if not title.strip(): raise ValueError("title required") return { "id": next_id(), "title": title, "due_date": due_date, "done": False, }

3 · git commit -m "feat: add task with due date (FR-1)"

Notice: you can explain every line — the empty-title check maps straight to FR-1's acceptance criterion. That's the standard.

▶ intro2se-w6-construction.fig · AI Critique #6
🧠 AI CRITIQUE #6 · LAST 10 MIN · ON A4

Spot it · explain it · fix it

"Just put the API key straight in the code and commit it — API_KEY = "sk-live-9f2a…". The repo is private, so it's fine."

— an AI coding assistant, confidently

1 · Spot

What's wrong?

A real secret (sk-live-…) is going into a commit — and into the shared history. Is "private repo" actually safe?

2 · Explain

Why is it wrong?

Once pushed, treat the key as leaked. Git keeps it in history even after you delete the line — and teammates, forks & a future public repo all carry it.

3 · Fix

The right way

Put it in .env, add .env to .gitignore, load from the environment. Already pushed? Revoke/rotate the key now — deleting the line is not enough.

Hand in your A4 before you leave — this is your attendance + AI-critique mark for the week.
