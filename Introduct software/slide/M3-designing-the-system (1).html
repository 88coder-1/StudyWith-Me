01 Mindset / กรอบความคิด

การออกแบบคืออะไร และทำไมต้องทำก่อนเขียนโค้ดWhat design is — and why it comes before code

ใน M2 คุณตอบว่า “ระบบต้องทำอะไร” (FR) และ “ดีแค่ไหน” (NFR) แล้ว ตอนนี้คำถามเปลี่ยนเป็น “แล้วจะสร้างมันยังไง” — ชิ้นส่วนของระบบมีอะไรบ้าง เก็บข้อมูลรูปทรงไหน แต่ละหน้าจอหน้าตายังไง และชิ้นส่วนคุยกันอย่างไร นั่นคือ Software Design

In M2 you answered what the system must do (FRs) and how well (NFRs). The question now becomes “so how will we build it?” — what parts the system has, what shape the data takes, what each screen looks like, and how the parts talk to each other. That's software design.

การออกแบบเกิดก่อนการเขียนโค้ดด้วยเหตุผลทางวิศวกรรม 3 ข้อ:Design precedes code for three engineering reasons:

  • แก้ไขที่ระดับโครงสร้างได้ก่อนลงทุนสร้าง ข้อผิดพลาดเรื่องโมเดลข้อมูลหรือการแบ่งชั้น ปรากฏชัดในไดอะแกรมและตารางตั้งแต่ยังไม่มีโค้ด จึงปรับได้ที่ระดับเอกสารStructural mistakes surface before you invest in building. Errors in the data model or the layering show up in a diagram or table while no code exists yet, so they're corrected at the document level.
  • ทีมทำงานขนานกันได้บนแบบเดียว เมื่อชิ้นส่วน โมเดลข้อมูล และหน้าตากลางถูกตกลงไว้ล่วงหน้า สมาชิกแต่ละคนสร้างส่วนของตนโดยไม่ชนกันThe team can work in parallel on one plan. With the parts, the data model, and a shared look agreed in advance, each member builds their piece without collisions.
  • AI สร้างได้ตรงและเร็ว เมื่อมีแบบระบุชัดว่าต้องมีเอนทิตี ชั้น และหน้าจออะไร AI สร้างตามข้อกำหนดได้ทันที ไม่ต้องเดาเจตนาThe AI builds accurately and fast. Given a plan that names the entities, layers, and screens, the AI implements to spec instead of guessing intent.
ต้นทุนการแก้ไขเพิ่มตามเฟส (cost-of-change)Cost of change rises with each phase หลักการที่ยืนยันด้วยงานวิจัยคลาสสิกของ Boehm: ต้นทุนในการแก้ข้อบกพร่องเพิ่มขึ้นอย่างมีนัยตามเฟสที่ค้นพบ — ข้อบกพร่องที่จับได้ในเฟสออกแบบใช้ต้นทุนแก้ต่ำที่สุด เพราะยังเป็นการปรับเอกสาร ไม่ใช่การรื้อโค้ดหรืองานที่ส่งไปแล้ว การใช้เวลากับ M3 จึงเป็นการลดต้นทุนรวมของโปรเจกต์โดยตรง A principle established by Boehm's classic study: the cost of fixing a defect rises significantly with the phase in which it is found. A defect caught during design costs the least to fix, because it is a document change rather than reworked code or shipped work. Time spent on M3 lowers the project's total cost directly.
ออกแบบไม่ใช่การเขียนโค้ดสวยDesign is not “pretty code” ในระดับวิชานี้ “design” หมายถึงการ ตัดสินใจเรื่องโครงสร้าง ก่อนลงมือ — ไม่ใช่การจัดฟอร์แมตโค้ด สิ่งที่คุณส่งใน M3 คือ เอกสารและภาพ (สถาปัตยกรรม, ไดอะแกรม, โมเดลข้อมูล, design system, prototype) ไม่ใช่แอปที่ทำงานได้ — แอปจริงไปอยู่ M4 At this level, “design” means structural decisions made before you build — not code formatting. What you submit in M3 is documents and pictures (architecture, diagrams, data model, design system, prototype), not a working app — the real app is M4.

02 The bridge / สะพานต่อจาก M2

จาก SRS สู่ design — ต่อยอดจาก requirement เดิมFrom SRS to design — built on the same requirements

M3 ไม่ได้เริ่มจากศูนย์ ทุกการตัดสินใจในการออกแบบต้อง ตอบ requirement ที่มีอยู่แล้ว ไม่ใช่คิดฟีเจอร์ใหม่ ถ้า design ชิ้นไหน “สาวกลับ” ไปหา FR/NFR ไม่ได้ แปลว่าคุณกำลังเพิ่มของที่ไม่มีใครขอ (gold-plating)

M3 doesn't start from zero. Every design decision must answer a requirement you already have, not invent a new feature. If a piece of your design can't “trace back” to an FR/NFR, you're adding something nobody asked for (gold-plating).

design ตอบ 3 คำถามที่ SRS ไม่ตอบ — โดยแต่ละคำถามผูกกลับไปที่ requirement เดิมDesign answers three questions the SRS deliberately left open — each tied back to the original requirements:

STRUCTURE

ระบบมีชิ้นส่วนอะไรWhat parts exist?

แบ่งเป็นชั้น/โมดูลอะไร คุยกันยังไง → สถาปัตยกรรม + ไดอะแกรมWhich layers/modules, and how they talk → architecture + diagrams

DATA

เก็บข้อมูลรูปทรงไหนWhat shape is the data?

เอนทิตี, ฟิลด์, ความสัมพันธ์, การกระทำ → โมเดลข้อมูลEntities, fields, relationships, operations → the data model

LOOK

หน้าตาเป็นยังไงWhat does it look like?

สี ฟอนต์ ปุ่ม และหน้าจอจริง → design system + prototypeColors, type, buttons, real screens → design system + prototype

กฎเหล็ก — ทุกอย่างต้องสาวกลับได้The iron rule — everything traces back FR-1 “เพิ่มงาน” → ต้องมีเอนทิตี Task, การกระทำ addTask, และหน้าจอ “เพิ่มงาน” ถ้าคุณวาดหน้าจอที่ไม่มี FR รองรับ ให้ลบทิ้ง ถ้ามี FR ที่ไม่มีหน้าจอ/ข้อมูลรองรับ แปลว่า design ยังไม่ครบ FR-1 “Add a task” → needs a Task entity, an addTask operation, and an “add task” screen. Draw a screen with no FR behind it → delete it. Have an FR with no screen/data behind it → the design isn't finished.

04 Architecture / สถาปัตยกรรม

สถาปัตยกรรม — แบ่งระบบเป็น 3 ชั้นArchitecture — split the system into three layers

สถาปัตยกรรมคือโครงระดับบนที่กำหนดว่าระบบประกอบด้วยส่วนใดบ้างและส่วนเหล่านั้นสื่อสารกันอย่างไร สำหรับแอปในระดับวิชานี้ ใช้รูปแบบมาตรฐาน 3 ชั้น (three-tier): หน้าตา → ตรรกะ → ข้อมูล ซึ่งครอบคลุมความต้องการทั้งหมดโดยไม่ซับซ้อนเกินจำเป็น

Architecture is the top-level structure defining which parts the system consists of and how those parts communicate. For an app at this level, use the standard three-tier pattern: presentation → logic → data — it covers every requirement without unnecessary complexity.

Three-tier pattern — each layer talks only to its neighbour

อ่านไดอะแกรม: แต่ละชั้นมี cohesion สูง (รวมเรื่องเดียวกันไว้ด้วยกัน) และคุยกับชั้นข้าง ๆ ผ่าน contract เท่านั้น = coupling ต่ำ · คำขอไหลลง คำตอบไหลขึ้น · ชั้นบนห้ามข้ามไปคุยกับชั้นล่างสุดโดยตรง — นี่คือ separation of concernsHow to read it: each layer has high cohesion (related things grouped) and talks to its neighbour only through a contract = low coupling · requests flow down, responses up · no layer skips to a non-adjacent one — that is separation of concerns.

1. ชั้นหน้าตา (UI / Presentation)1. Presentation layer (UI)what the user sees
หน้าจอ ปุ่ม ฟอร์ม — รับ input จากผู้ใช้และแสดงผล ไม่เก็บกฎธุรกิจ (เช่น หน้า “เพิ่มงาน”, dashboard “สัปดาห์นี้”)Screens, buttons, forms — take user input and show results. Holds no business rules (e.g. the “add task” screen, the “this week” dashboard).

2. ชั้นตรรกะ (Logic / Application)2. Logic layer (application)the rules
กฎและการกระทำ — “เตือนหนึ่งวันก่อนกำหนดส่ง”, “ผู้ใช้เห็นเฉพาะงานของตัวเอง” นี่คือที่อยู่ของ FR/NFR ในโค้ดRules and operations — “remind one day before the due date,” “a user sees only their own tasks.” This is where your FRs/NFRs live in code.

สองเกณฑ์ที่ใช้วัดคุณภาพของการแบ่งส่วน: Cohesion & CouplingTwo criteria for judging how you split the system: cohesion & coupling

เป้าหมาย: สูงtarget: high

Cohesion — ความเกาะกลุ่มภายในส่วนinternal focus

แต่ละส่วนรวมเฉพาะสิ่งที่เกี่ยวข้องกันไว้ด้วยกัน เช่น ตรรกะเรื่อง “การเตือน” ทั้งหมดอยู่ในส่วนเดียว ทำให้ค้นหาและแก้ไขได้ตรงจุดEach part groups only things that belong together — e.g. all reminder logic sits in one part — so it is found and modified in one place.

เป้าหมาย: ต่ำtarget: low

Coupling — การพึ่งพาระหว่างส่วนinter-part dependence

ส่วนต่าง ๆ ควรสื่อสารกันผ่านสัญญา (contract) ที่ระบุชัด ไม่เข้าถึงภายในของกันและกันโดยตรง เพื่อให้การแก้ส่วนหนึ่งไม่กระทบส่วนอื่นParts should communicate through a defined contract, never reaching into each other's internals, so a change in one part does not affect another.

Separation of concernsSeparation of concerns แต่ละชั้นทำหน้าที่ของตัวเองเรื่องเดียว — หน้าจอไม่ตัดสินกฎ, ตรรกะไม่วาดปุ่ม, ข้อมูลไม่รู้ว่าใครเรียกใช้ ทำแบบนี้แล้วเปลี่ยนหน้าตาไม่กระทบกฎ เปลี่ยนที่เก็บข้อมูลไม่กระทบหน้าจอ — และ AI แก้ทีละชั้นได้โดยไม่พังส่วนอื่น Each layer minds its own one job — the UI decides no rules, the logic draws no buttons, the data doesn't know who calls it. Then changing the look doesn't touch the rules, changing storage doesn't touch the screens — and the AI can edit one layer without breaking the others.

หลายสไตล์ใช้ร่วมกัน — เลือก “รูปที่เล็กที่สุดที่พอดี”Several styles at once — pick the smallest shape that fits

09 Smells / กลิ่นไม่ดี

10 กลิ่นไม่ดีของ design — เจอแล้วแก้ก่อนส่ง10 design smells — fix them before you submit

“design smell” คือสัญญาณที่บ่งชี้ว่าการออกแบบมีปัญหาเชิงโครงสร้างซึ่งควรแก้ก่อนลงมือสร้าง ตรวจ design ของคุณกับรายการต่อไปนี้

A “design smell” is a signal that the design has a structural problem worth fixing before you build. Check your design against the following list.

  1. ออกแบบเกิน (over-engineering / YAGNI)Over-engineering (YAGNI)ใส่ระบบ plugin, microservices, cache หลายชั้น ทั้งที่โปรเจกต์มี 4 FR — “You Aren't Gonna Need It”Plugins, microservices, multi-layer caches for a 4-FR project — “You Aren't Gonna Need It.”
  2. Gold-platingGold-platingหน้าจอ/ฟีเจอร์สวยหรูที่ไม่มี FR รองรับ — ลบทิ้งA shiny screen/feature no FR asks for — delete it.
  3. รั่วเทคโนโลยีเข้า “โมเดลข้อมูล logical”Tech leaked into the logical data modelเขียน Firestore doc.set()/React state ปนใน โมเดลข้อมูล (เอนทิตี/ฟิลด์) · การเลือก Firebase ที่ชั้น architecture/deployment ไม่นับเป็น smell (ดู §4)Firestore doc.set()/React state mixed into the data model (entities/fields) · naming Firebase at the architecture/deployment level is fine (see §4).
  4. Coupling สูงHigh couplingหน้าจอเขียนกฎธุรกิจเอง แก้ที่หนึ่งพังอีกที่The UI holds business rules; change one place, another breaks.
  5. Cohesion ต่ำ (God component)Low cohesion (God component)กล่องเดียวทำทุกอย่าง — ทั้ง UI ตรรกะ และข้อมูลOne box does everything — UI, logic, and data.
  6. หน้าจอไม่มีทางที่ผิดNo error/empty statesมีแต่ตอนสมบูรณ์ ไม่มี “ไม่มีข้อมูล/กรอกผิด/โหลดอยู่”Only the happy case — no “empty/invalid/loading.”
  7. ค่าปริศนา (magic values)Magic valuesสี/ตัวเลขลอย ๆ ในหน้าจอ ไม่ผ่าน design tokenStray colors/numbers in screens, not via tokens.
  8. FR ไม่มีที่อยู่ใน designAn FR with no homeมี FR แต่ไม่มีเอนทิตี/หน้าจอ/operation รองรับAn FR with no entity/screen/operation behind it.
  9. ไดอะแกรมไม่ตรงข้อความDiagram contradicts the textภาพวาดอย่าง เขียนอีกอย่าง — ทีมสับสนThe picture says one thing, the prose another — the team gets confused.
  10. ปรับแต่งเร็วเกิน (premature optimization)Premature optimizationห่วงความเร็วระดับล้านผู้ใช้ ทั้งที่ยังไม่มีแอป — ทำให้ถูกก่อน ค่อยทำให้เร็วWorrying about million-user speed with no app yet — make it right, then fast.
หลักคิดกันเกิน: “ง่ายที่สุดที่ยัง(พอ)ใช้ได้”The antidote: “the simplest thing that still works” เป้าหมายของ design ในวิชานี้ไม่ใช่ “อลังการ” แต่คือ เล็กที่สุดที่ตอบทุก Must FR ได้จริง ถ้าลังเลว่าจะใส่หรือไม่ใส่ ให้ถามว่า “FR ไหนบังคับให้มี” ตอบไม่ได้ = ไม่ใส่ The goal here isn't grandeur; it's the smallest design that truly satisfies every Must FR. When unsure whether to add something, ask “which FR forces this?” No answer = leave it out.

10 AI-First / ออกแบบด้วย AI

ออกแบบด้วย AI — คุณตัดสินใจ AI ลงรายละเอียดDesign with AI — you decide, the AI fills in the detail

AI วาดไดอะแกรม ร่างโมเดลข้อมูล และสร้าง prototype ได้เร็วมาก แต่มัน ไม่รู้ว่าอะไรคือ “พอดี” สำหรับโปรเจกต์คุณ — มันมักออกแบบเกิน หน้าที่ของคุณคือให้ทิศทาง ตัดสินใจ และตัดของเกินออก
